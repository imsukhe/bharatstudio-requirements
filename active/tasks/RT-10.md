## Boundaries

**In scope:** an in-memory admission governor (`read-backpressure.ts`) over `derived_read`-classified GET requests, keyed off one shared classifier (`read-priority.ts`) RT-10 and RT-11 both use; an optional isolated connection pool for exactly the five read-only overlay/dashboard stores this task wires to it (`overlayGoals`, `overlayChallenges`, `interactionOverlay`, `paidVoteOverlay`, `paymentLedger` — all nine named widgets plus the payment ledger dashboard read, verified read-only with no INSERT/UPDATE/DELETE in any of their source files before wiring); a `503 derived_read_shed` retryable response shed before any database work starts; two new RT-06-style counters.

**Explicitly out of scope, not touched:** RT-07 (blocked), RT-09 (a marketing gate), RT-13, PRF-02/Master Canvas, anything YouTube, marketing or pricing copy, tier/entitlement changes, the TTS path (RT-03), the webhook acknowledgement and dispatch lease (RT-04/RT-05 — payment-webhook-go and alert-worker-go have their own separate database connections in a separate Go service and are never touched by this TypeScript-only mechanism), the wake-up coalescing follow-up recorded in `TC-RT-04`, the dead `target_after_created_at`/`target_after_delivery_id` parameters in `app_private.get_overlay_events`, and `bharatstudio-crons`. No register state letter changed — §31.18.0's `A` for RT-10 is left exactly as it reads; Opus decides after audit.

**A factual correction to this task's own briefing, found during implementation, recorded here per the operator's "if something is factually wrong about the code, STOP and report it" rule.** The command that opened this row asserted `apps/api/src/app.ts` "uses `max: 120`" as evidence that a large main pool already exists. That is incorrect: `app.ts:197`'s `max: 120` is the `@fastify/rate-limit` plugin's **requests-per-minute** cap, not a database pool. The actual main connection pool is created in `apps/api/src/db/public-channel-repository.ts`'s `createSqlClient`, at **`max: 10`**, and is the single `sql` instance `index.ts` passes to nearly every store in the application — there is no `max: 120` database pool anywhere in this codebase. This does not invalidate the row: the "a separate pool for a separate class of work is already an established pattern here" observation still holds on its own merits (`public-channel-repository.ts` max 10, `overlay-wakeup.ts` max 1, `template-import-runner.ts` max 1), and `DEFAULT_DERIVED_POOL_MAX` in `derived-read-pool.ts` reuses the codebase's real existing precedent (10, not 120) — see the review record for the corrected derivation and why 120 was never used as a baseline for any decision in this row.

## Classification (payment-class vs. widget/analytics-class vs. unclassified)

`classifyReadPriority(method, route)` (`apps/api/src/domain/read-priority.ts`) is the single answer, shared by RT-10 and RT-11:

- **Structurally exempt, always:** every non-GET request. Every payment write, webhook commit, alert delivery and overlay event this TypeScript API exposes is a POST/PUT/DELETE, or lives entirely in a separate Go service (`payment-webhook-go`, `alert-worker-go`) with its own connections this module never touches. The governor is only ever consulted from a GET-scoped `onRequest` check — a write is never even asked.
- **Explicitly exempt GET reads (durable/payment-adjacent):** `/v1/overlays/:overlayId/events` (the RT-01/RT-02 durable SSE stream), `/v1/overlays/:overlayId`, `/v1/overlays/:overlayId/cursor`, `/v1/public/tip-orders/:orderId/status`, `/v1/public/tip-intents/:token` (a supporter reading their own payment's status — a read leg of the payment flow, not a derived/aggregate view), plus operational routes (`/internal/*`, `/healthz`, `/readyz`).
- **Everything else GET — the fail-safe default — is `derived_read`, governed.** This is deliberate and matches §2 of the owning command: an unclassified route must fail toward the **lower** priority, never be silently treated as payment-class. In practice this governs the nine named widget snapshot routes, the payment ledger dashboard route, and any other GET route an operator has not (yet) named exempt — all subject to the SAME configured ceiling, none subject to it by accident being read as payment-class.

## Mechanism

Two independent, additive, both-unset-by-default protections (§2 of the owning command — no invented number):

1. **Admission governor (`read-backpressure.ts`).** An in-memory concurrency counter over `derived_read` requests. `WIDGET_ANALYTICS_MAX_CONCURRENT_READS` unset ⇒ no ceiling, nothing ever shed. Set ⇒ the `(ceiling+1)`th concurrent derived read is rejected with `503 derived_read_shed` before any database work starts (admission is synchronous, no I/O, never throws — a metrics-callback failure cannot break admission).
2. **Isolated pool (`derived-read-pool.ts`, shared with RT-11).** `WIDGET_ANALYTICS_POOL_MAX` unset ⇒ the five governed stores keep sharing the main `sql` pool exactly as before this task. Set ⇒ a second, bounded `postgres()` pool is created and wired to those five stores only (`index.ts`'s `derivedReadSql`), so a widget/analytics burst can never consume connections the payment-order write path needs — that path always uses the main pool, untouched.
