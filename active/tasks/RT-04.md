## Boundaries

**In scope:** `services/payment-webhook-go/internal/ingress/handler.go` — the post-commit wake-up (`h.Pumper.Pump(...)`) moves from synchronous-and-response-gating to a fire-and-forget goroutine (`Handler.wakeUpDispatcher`) that cannot influence the status code, using `context.Background()` (not the request context, which is cancelled once the response is written) so the goroutine outlives the request without ever leaking past `WorkerPumpClient`'s own bound; a new `Metrics.ObserveWakeupOutcome` (`kind="wakeup"`, outcomes `succeeded`/`failed`) and the existing `Logger.Event("webhook_wakeup", ...)` shape record the outcome without ever touching the response. `services/alert-worker-go`'s pump (`internal/tasks/pump.go`, `internal/handler/pump.go`, `cmd/alert-worker/main.go`) gains an optional `DispatchLeaser` — when configured (production wiring only; every pre-existing test leaves it nil and is unaffected), `Pump.RunOnce` acquires a single-row mutual-exclusion lease before scanning and releases it on a graceful return, so two concurrent dispatch runs never both list and enqueue the same backlog (RT-05); losing the race is a clean `Skipped` outcome, not an error. `packages/db/migrations/0129_v1_rt04_rt05_outbox_dispatch_lease.sql` adds `app_private.outbox_dispatch_lease` (one singleton row) and `acquire_outbox_dispatch_lease`/`release_outbox_dispatch_lease`, reusing the exact `lease_token`/`lease_until` acquire-if-unheld-or-expired discipline `app_private.claim_event_delivery` (0004/0022/0063) already uses, at a coarser (one-dispatch-run, not one-delivery) grain — deliberately not the same field, see "Design decisions" below. `bharatstudio-crons/schedules/v1.json` sets `outbox-recovery.enabled` to `true` — the only schedule touched; `tests/schedule-contract.test.mjs` and `docs/SCHEDULER_OPERATIONS.md` are updated to state and explain that change honestly.

## Design decisions this command did not settle

1. **The dispatch lease is a new single-row control table, not a second write to `event_outbox_deliveries.lease_token`/`lease_until`.** The obvious-looking alternative — lease the *rows themselves* at scan time, reusing the per-delivery field `claim_event_delivery` already sets — was considered and rejected: that field's own `WHERE` clause (`lease_until is null or lease_until <= current_timestamp`) is also the gate `claim_event_delivery` itself checks at real dispatch time. Setting it during the scan step would make the *real* per-delivery claim (fired by the enqueued Cloud Task, normally within milliseconds of enqueue) wait out the *scan* lease's full TTL on every normal delivery, not just a missed one — trading a rare double-scan for a latency regression on the common path. A single, coarser "one dispatch run at a time" lease, using the identical token+expiry acquire-if-unheld-or-expired shape at process granularity instead of per-delivery granularity, gives RT-05's safety property (no two runs enqueue the same backlog) without that regression, and does not touch the real per-delivery claim path at all. Recorded as the correct call, not deferred, but flagged here because it is the one place this task diverged from the most literal reading of "reuse the lease_token/lease_until discipline."
2. **Lease TTL is 60 seconds and scan batch is unchanged (still capped at 500 inside `list_ready_event_deliveries`)** — both are pre-existing numbers (the `outbox-recovery` schedule's own `timeoutSeconds`, and 0063's existing `least(...,500)` cap), per the operator's explicit instruction not to invent one. No new numeric limit was introduced anywhere in this task.
3. **The wake-up call shape (an HTTP POST to the alert-worker's `/internal/v1/tasks/pump`) is unchanged** — only its position relative to the response changed (fire-and-forget instead of blocking-and-response-gating). It was not redesigned into a narrower, per-delivery-targeted signal (e.g. carrying the specific delivery IDs just committed), which would reduce the pump's own scan cost further but is a larger change to the wake-up's shape than "make it fire-and-forget" calls for. Left as a candidate follow-up, not implemented here.
4. **RT-05 and RT-08's own `active/traceability/register-map.tsv` and `semantic-mapping-audit.md` rows are left untouched (`new-record-required`)**, even though both are implemented as consequences of this task's change (§3.4 of the operator's command: "do not change any register state letter — Opus decides all three after audit"). `tools/traceability.py` requires an `active-record` lifecycle row's task target filename to match the ID exactly (`{rid}.md`), so pointing RT-05/RT-08 at this file while marking them `active-record` would fail validation, and creating separate `RT-05.md`/`RT-08.md` files whose entire content restates this same change would violate `governance/AGENTS.md`'s "do not create duplicate documents." Only `RT-04`'s own row moves to `active-record`. This paragraph, the review record, and this task record are how "which of RT-04/RT-05/RT-08 each change serves" (the operator's own requirement) is made clear instead.

## Correction, 2026-09-16 — wake-up coalescing

**Owner:** Sukhdev Singh
**Status of this correction:** `Implemented — local verification only; independent review unavailable`

Closes the finding recorded in `../../reviews/2026-09-16-rt-04-webhook-commit-and-leased-dispatcher.md` ("The post-commit wake-up spawns one goroutine per webhook with no coalescing"). That finding was raised and deliberately not fixed at the time. It is fixed now.

**What changed.** `services/payment-webhook-go/internal/ingress/wakeup_coalescer.go` (new) introduces `WakeupCoalescer`. `Handler` gains a `Wakeups *WakeupCoalescer` field; `wakeUpDispatcher` hands its demand to the coalescer instead of starting a goroutine per webhook, and the actual call moves to a new `Handler.runWakeup`. `cmd/payment-webhook/main.go` constructs one coalescer, shares it across every webhook request, and closes it on every return path — for the graceful path, after `server.Shutdown` has drained in-flight requests. The `context.Background()` property is unchanged and kept for its recorded reason: the request context is cancelled once `ServeHTTP` returns.

**The invariant implemented.** At most one wake-up goroutine exists per coalescer and at most one wake-up is in flight; demand arriving while one is in flight sets a single boolean `pending` flag rather than queueing. `pending` is cleared under the same mutex immediately before the run that satisfies it, and the goroutine's exit branch clears `running` under that same mutex — so a request that observed `running == true` necessarily happened before the exit check, and that check therefore sees `pending` and runs once more instead of exiting. Consequence: after any accepted webhook, at least one complete wake-up run *begins* after that webhook recorded its demand. A wake-up already in flight causes exactly one more after it completes, never zero. The last wake-up of a burst is never the one dropped.

**Bound, derived structurally — no number invented, no config value added.** One coalescer per dispatcher target, one goroutine per coalescer, one boolean flag instead of a queue. §12.7 bounded data is satisfied by construction: there is no map, no queue, and no per-identity state that can grow with traffic.

**"Per channel", stated plainly rather than papered over.** The operator's instruction asked for "at most one in flight per channel". This path has no channel. `webhook.Delivery` carries only `ProviderEventID` and `RawBodyHash`, and the wake-up is an HTTP POST of `{}` to the alert-worker's single `/internal/v1/tasks/pump` endpoint — design decision 3 above deliberately left that shape unchanged. There is therefore exactly one wake-up target per process and exactly one coalescing domain, so the coalescer is keyed on that single target, not on a channel. This is **stronger** than per-channel coalescing (a burst spanning many channels also collapses to a bounded number of wake-ups) and it is the §12.7-correct choice: a per-channel map would be state keyed by externally-controlled identity, growing with traffic. Adding a channel key would require changing the wake-up's shape, which this correction does not do.

**The response path is untouched.** `request` takes a mutex and returns; it never blocks, so the 2xx still does not wait on a wake-up. Every RT-04.1–RT-04.5 acknowledgement property is unchanged and its tests still pass.

**Shutdown.** `Close` sets a flag under the mutex, clears `pending`, and is idempotent. It closes no channel and writes to nothing torn down, so a request racing it cannot panic or write after close — it takes the mutex, sees `closed`, and returns. A wake-up already in flight finishes on `WorkerPumpClient`'s existing timeout; one merely owed is abandoned. Nothing is lost by abandoning it: the durable commit already happened and the `outbox-recovery` sweep re-enqueues whatever a missed wake-up delayed.

**One stated reason for the original deferral did not hold.** The review expected this to require restructuring `ingress.Handler` from a struct literal into a constructor. It did not: the coalescer is an exported pointer field on the existing struct, so every existing call site kept its literal form. The other reason for deferral — that the load threshold at which this matters cannot be measured locally (ENV-08, RT-07, both Blocked) — still stands, and nothing in this correction claims otherwise.

**Two pre-existing test items changed, deliberately.** `countingPumper` no longer counts down a WaitGroup sized to the burst, and RT-04.10's `TestBurstOfWebhooksDoesNotLeakWakeupGoroutines` no longer asserts that 200 webhooks produce exactly 200 wake-ups — that assertion *was* the defect. It now asserts at least one wake-up and strictly fewer than 200, with all 200 commits still asserted intact. Coalescing collapses the hint, never the commit.

**Residual, recorded rather than hidden.** A `Handler` constructed without a `Wakeups` coalescer still falls back to one goroutine per webhook. That path is unreachable in production — `cmd/payment-webhook/main.go` is the only production construction site and always sets the field — and the fallback exists because silently dropping the wake-up would be the worse failure. Every test in `internal/ingress` was updated to supply a coalescer, so the coalesced path is the one under test.

**What this evidence is and is not.** Local only: `go build ./...`, `go vet ./...` and `go test -race ./...` inside `services/payment-webhook-go`, plus negative-test runs that break the coalescing and show the new test fail. **No production, provider, staging, load or performance evidence is claimed.** The burst sizes in the tests (64, 200) are test fixtures, not a measured production burst, and no threshold at which coalescing begins to matter in production has been measured — that remains ENV-08/RT-07 work and both are Blocked. No migration, API route, OpenAPI contract, or file outside `services/payment-webhook-go` was touched. Nothing is committed; the change is left in the working tree for review.
