## Boundaries

**In scope:** `services/payment-webhook-go/internal/ingress/handler.go` — the post-commit wake-up (`h.Pumper.Pump(...)`) moves from synchronous-and-response-gating to a fire-and-forget goroutine (`Handler.wakeUpDispatcher`) that cannot influence the status code, using `context.Background()` (not the request context, which is cancelled once the response is written) so the goroutine outlives the request without ever leaking past `WorkerPumpClient`'s own bound; a new `Metrics.ObserveWakeupOutcome` (`kind="wakeup"`, outcomes `succeeded`/`failed`) and the existing `Logger.Event("webhook_wakeup", ...)` shape record the outcome without ever touching the response. `services/alert-worker-go`'s pump (`internal/tasks/pump.go`, `internal/handler/pump.go`, `cmd/alert-worker/main.go`) gains an optional `DispatchLeaser` — when configured (production wiring only; every pre-existing test leaves it nil and is unaffected), `Pump.RunOnce` acquires a single-row mutual-exclusion lease before scanning and releases it on a graceful return, so two concurrent dispatch runs never both list and enqueue the same backlog (RT-05); losing the race is a clean `Skipped` outcome, not an error. `packages/db/migrations/0129_v1_rt04_rt05_outbox_dispatch_lease.sql` adds `app_private.outbox_dispatch_lease` (one singleton row) and `acquire_outbox_dispatch_lease`/`release_outbox_dispatch_lease`, reusing the exact `lease_token`/`lease_until` acquire-if-unheld-or-expired discipline `app_private.claim_event_delivery` (0004/0022/0063) already uses, at a coarser (one-dispatch-run, not one-delivery) grain — deliberately not the same field, see "Design decisions" below. `bharatstudio-crons/schedules/v1.json` sets `outbox-recovery.enabled` to `true` — the only schedule touched; `tests/schedule-contract.test.mjs` and `docs/SCHEDULER_OPERATIONS.md` are updated to state and explain that change honestly.

## Design decisions this command did not settle

1. **The dispatch lease is a new single-row control table, not a second write to `event_outbox_deliveries.lease_token`/`lease_until`.** The obvious-looking alternative — lease the *rows themselves* at scan time, reusing the per-delivery field `claim_event_delivery` already sets — was considered and rejected: that field's own `WHERE` clause (`lease_until is null or lease_until <= current_timestamp`) is also the gate `claim_event_delivery` itself checks at real dispatch time. Setting it during the scan step would make the *real* per-delivery claim (fired by the enqueued Cloud Task, normally within milliseconds of enqueue) wait out the *scan* lease's full TTL on every normal delivery, not just a missed one — trading a rare double-scan for a latency regression on the common path. A single, coarser "one dispatch run at a time" lease, using the identical token+expiry acquire-if-unheld-or-expired shape at process granularity instead of per-delivery granularity, gives RT-05's safety property (no two runs enqueue the same backlog) without that regression, and does not touch the real per-delivery claim path at all. Recorded as the correct call, not deferred, but flagged here because it is the one place this task diverged from the most literal reading of "reuse the lease_token/lease_until discipline."
2. **Lease TTL is 60 seconds and scan batch is unchanged (still capped at 500 inside `list_ready_event_deliveries`)** — both are pre-existing numbers (the `outbox-recovery` schedule's own `timeoutSeconds`, and 0063's existing `least(...,500)` cap), per the operator's explicit instruction not to invent one. No new numeric limit was introduced anywhere in this task.
3. **The wake-up call shape (an HTTP POST to the alert-worker's `/internal/v1/tasks/pump`) is unchanged** — only its position relative to the response changed (fire-and-forget instead of blocking-and-response-gating). It was not redesigned into a narrower, per-delivery-targeted signal (e.g. carrying the specific delivery IDs just committed), which would reduce the pump's own scan cost further but is a larger change to the wake-up's shape than "make it fire-and-forget" calls for. Left as a candidate follow-up, not implemented here.
4. **RT-05 and RT-08's own `active/traceability/register-map.tsv` and `semantic-mapping-audit.md` rows are left untouched (`new-record-required`)**, even though both are implemented as consequences of this task's change (§3.4 of the operator's command: "do not change any register state letter — Opus decides all three after audit"). `tools/traceability.py` requires an `active-record` lifecycle row's task target filename to match the ID exactly (`{rid}.md`), so pointing RT-05/RT-08 at this file while marking them `active-record` would fail validation, and creating separate `RT-05.md`/`RT-08.md` files whose entire content restates this same change would violate `governance/AGENTS.md`'s "do not create duplicate documents." Only `RT-04`'s own row moves to `active-record`. This paragraph, the review record, and this task record are how "which of RT-04/RT-05/RT-08 each change serves" (the operator's own requirement) is made clear instead.
