## Design decisions this command did not settle

1. **`TtsQuotaMeter.release` is a required interface member**, not optional, unlike `TtsStore.storeFallbackReason` (which stays optional/back-compat). Reasoning: RT-03.6 is named a blocking acceptance test in the operator's command, and quota-charge correctness should not depend on every future caller remembering to implement an optional method. The three existing test files with pre-existing `TtsQuotaMeter` fakes (`apps/api/test/tts-quota-metering.test.ts`, `apps/api/test/l07-mute-synthesis-cost-gate.test.ts`, `apps/api/test/tts-fallback-reason.test.ts`) were mechanically updated (10 object literals, each gaining `async release() {}`) — no assertion in any of those pre-existing tests was changed.
2. **`app_private.release_tts_usage_reservation` operates on the existing `alert_tts_usage_monthly` accumulator column**, not a new ledger table. §10.2's grant/reserve/settle/release/refund/expiry vocabulary describes the AI-credits ledger conceptually; the TTS character quota's actual implementation (`0081`) is a per-channel/per-month counter, not literal ledger rows with an `entry_type` column. This task's release function decrements that counter (floored at zero via `greatest(...,0)`), which is a release over the existing mechanism, not a new one — consistent with the operator's instruction to follow the codebase's existing reserve/settle/release shape rather than invent a new entry type.
3. **A 5xx or a 429-with-`Retry-After` from the internal TTS route is classified retryable-unambiguous** on the reasoning that a complete HTTP response (status line and headers received) means the request definitely reached `apps/api`'s internal route and got a definitive answer, and — after this task's own quota-release fix — that answer is guaranteed to have already released any reservation before the error response left the route. This is an inference from the current single-hop worker→API topology (not a literal "5xx before any response body" byte-level distinction, which Go's `http.Client` does not expose at this call site) and is recorded as `Unverified` in the review.
4. **No new metric was added.** RT-06 (histograms) is explicitly out of scope for this task, and RT-02's precedent of adding bounded *counters* was not repeated here because the operator's command for this task lists only `Logger.Event` (not a metrics counter) under the privacy/security section for the Go side. If a bounded `tts_enrich` outcome counter is later wanted for operability, that is additive and does not require reopening this task.
5. **The register-map.tsv / semantic-mapping-audit.md `state` cell for `RT-03` is left at `X`**, matching `FULL-PRODUCT-DEFINITION.md` §31.18.0's own `RT-03` row, which this command explicitly says not to change. `lifecycle` moves from `new-record-required` to `active-record` since a real ten-field record now exists, mirroring RT-02's precedent exactly.

## Correction, 2026-09-16 — migration `0134`, release by reservation id

**What was wrong.** `0128` closed the live billing defect (a failed synthesis
permanently consumed premium characters) but left two correctness properties
unenforced, and documented them in its own comments instead of fixing them.
Both were found by re-reading `0128` against this task's own written contract,
not by a check.

1. **`release_tts_usage_reservation(uuid, integer)` was not idempotent.** The
   `greatest(...,0)` floor prevents a negative counter and nothing else.
   A second release against a billing month that holds **other** usage
   subtracts a second time and hands the creator characters nobody reserved.
   `0128`'s comment named the problem and delegated it: "the invariant that
   prevents it lives in the caller ... any future caller must hold the same
   invariant." That is a correctness property with no enforcement — the same
   shape as every §2 finding in this register, one layer down.
2. **Release credited the wrong billing month.** It updated
   `date_trunc('month', current_timestamp)`, not the month the reservation was
   actually charged to. Reserve and release sit either side of one provider
   call, so a UTC month boundary between them is rare but real. `0128` called
   this "a safe no-op", which holds only when the new month has no usage row.
   When it does, the old month keeps the charge **and** the new month is
   credited characters it never reserved. That directly contradicts the
   `TtsQuotaMeter` interface's own written contract, which already said
   release "must never manufacture quota that was not reserved".

**Why no test caught it.** `packages/db/tests/rt03_tts_quota_reservation_release.sql`
asserted idempotency and **passed** — but it released a month whose counter had
already reached `0`, the one arrangement where the floor hides the missing
property. It never tested a double release against a month holding other usage,
and never tested a rollover at all. A green check blind to the case it was never
told about.

**The fix.** Reservations become durable rows
(`public.alert_tts_usage_reservations`). `meter_tts_usage` records what it
charged and to which billing month, and returns the reservation id as a fourth
column; `release_tts_usage_reservation(uuid)` consumes that id exactly once and
credits the month stored on the reservation. Idempotency and month-correctness
become properties of the schema rather than of the caller's discipline. The
`(uuid, integer)` signature is **dropped**, not left alongside — leaving the
non-idempotent function callable would preserve the defect for the next caller.

**This supersedes "Design decisions this command did not settle" item 2**,
which recorded that the release "operates on the existing
`alert_tts_usage_monthly` accumulator column, not a new ledger table". That
reasoning was sound for a release keyed by character count and is wrong for the
properties this correction needs: a counter cannot carry per-reservation state,
and per-reservation state is exactly what idempotency and month-correctness
require. The new table is still **not** a §10.2 entry-type ledger — it has no
`entry_type` column and no grant/settle/refund/expiry vocabulary. It is
reservation state over the same counter, which `alert_tts_usage_monthly`
remains the source of truth for.

**Deliberate narrowing.** Release is now all-or-nothing per reservation.
`0128` accepted an arbitrary character count, making "release less than was
reserved" expressible; no caller ever used it (`apps/api/src/routes/tts.ts`
always released the full metered amount on three mutually exclusive paths) and
it is not a §10.2 entry type. Removing it removes a class of arithmetic error
rather than testing around it.

**No new personal-data class.** The reservation row carries `channel_id`, a
character count, a billing month and timestamps. No viewer, no payment, no
message text, and no identifier that reaches a log or a metric label. The table
carries the same posture as `alert_tts_usage_monthly` (`0081`): RLS enabled,
all privileges revoked from `bsa_app`, reachable only through the two
security-definer functions — asserted directly in the acceptance test.
