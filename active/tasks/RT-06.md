## Boundaries

**In scope:** bucketed histogram metrics, derived exclusively from §19.4's stated budget numbers, on every path this task could identify as carrying one of those two numbers: the TS API's read paths (`bsa_api_read_duration_ms`, 200ms boundary) and the tip-order creation path (`bsa_api_tip_order_duration_ms`, 500ms boundary; plus `services/payment-webhook-go`'s own leg of the same path, `bsa_payment_tip_order_duration_ms`, same 500ms boundary). A bucket-interpolated p95/p99 read-out for every new histogram, with HELP text stating the estimate's error bound explicitly (§3.2). The additive property cross-instance aggregation depends on, proven locally as a pure-function property (`mergeHistograms` in TS, `MergeHistograms` in both Go services) and exercised by `-race`-clean concurrent Observe/scrape tests. Durable, cross-instance-correct storage for the L09 reliability-reconciliation snapshot (migration `0130`, forward-only, next free number after `0129`), closing the "reconciliation snapshots are process-local" half of RT-06's own defect text. Two additional histograms, reasoned (not invented) classifications explicitly recorded in the review record: `services/payment-webhook-go`'s `/v1/webhooks/razorpay` webhook-acknowledgement path (measured under the tip-order-class 500ms bucket set, per §3.5's explicit invitation to add measurement to that path) and `services/alert-worker-go`'s `/internal/v1/tasks/pump` dispatch path (measured under the read-class 200ms bucket set, as the closer analogue of the two budgeted classes).

**Explicitly out of scope, not touched:** RT-07 (browser/OBS/device/load evidence — this task builds the instrument, it produces no readings), RT-09 through RT-13, PRF-02/Master Canvas, anything YouTube, marketing or pricing copy, tier/entitlement changes, the TTS path (RT-03), the webhook acknowledgement path's and dispatch lease's *behaviour* (RT-04/RT-05 — only measurement was added, per §3.5's explicit allowance; no ordering, timing or response-shaping logic in either path changed), the wake-up coalescing follow-up recorded in `TC-RT-04`, and the dead `target_after_created_at`/`target_after_delivery_id` parameters in `app_private.get_overlay_events`. No register state letter changed (§31.18.0's `A` for RT-06 is left exactly as Opus's own §31.18.1/§31.18.0 table already reads — Opus decides state letters after audit). `bharatstudio-crons/schedules/v1.json` was **not** modified — see "Referred to Opus" in the review record for why `payment-reconciliation` was not the schedule this task could genuinely wire, and why it was left disabled rather than flipped.

## Design decisions this command did not settle

1. **Bucket boundaries are derived, and the derivation is recorded in the review record, not asserted here.** Every histogram this task adds carries §19.4's own stated number (200 or 500) as an exact bucket boundary; every other boundary in the same set is measurement resolution around that number, justified individually in `reviews/2026-09-16-rt-06-budget-histograms.md`. Two paths — the webhook acknowledgement path and the dispatcher's pump trigger — carry no numeric §19.4 row of their own; both were classified into one of the two existing budget classes by reasoned analogy (payment-commit-and-respond vs. bounded-internal-operation) rather than left uninstrumented or given an invented third number. This is flagged, not hidden, in both the code comments at each classification site and the review record.
2. **`payment-reconciliation` in `bharatstudio-crons/schedules/v1.json` was investigated and deliberately left disabled.** The operator's command names it as "the reconciler's schedule," but its actual `target.path` is `/internal/v1/reconciliation/payments` on `payment-webhook-go` — an already-implemented, unrelated Razorpay provider-status recovery mechanism (`services/payment-webhook-go/internal/reconcile/handler.go`) — not the L09 reliability-snapshot reconciler RT-06's own defect text names (`apps/api/src/routes/metrics.ts`'s `POST /internal/metrics/reconcile`, called by nothing in the schedule catalogue). Enabling `payment-reconciliation` would not close RT-06's "the reconciler schedule is unwired" defect and would misrepresent progress against it. Per the operator's own instruction ("a schedule pointing at unwired code is worse than a disabled one" — and, symmetrically, enabling a *correctly wired but unrelated* schedule under this task's name would misattribute it), this was referred to Opus rather than acted on. Full reasoning in the review record.
3. **The reconciliation snapshot's durable table is a singleton, upserted wholesale, not an append-only history.** This matches the in-memory variable it replaces exactly (`setReconciliationSnapshot` always fully replaces, never merges) and matches migration `0129`'s own `outbox_dispatch_lease` precedent for a one-row `app_private` control table reachable only through `SECURITY DEFINER` functions, never direct table access.
4. **No behavioural change to RT-04/RT-05's response paths.** Every new `Observe`/`observeHistogram` call site was checked against the fire-and-forget/lease-coordinated designs those tasks already verified `-race`-clean; RT-06 adds observation calls inside the same code paths without adding a blocking call, a lock acquisition outside the existing `Metrics.mu`, or any new I/O on the request path.
