## What this proves and what it does not — stated as plainly as the operator's command requires

**The local database this task captured against is not seeded to §37.4's size** (500 channels · 2,000,000 payments · 5,000,000 alert events · 200,000 supporter identities; ENV-02 is `Conditionally complete`, the full-volume gate is open). Every artifact in `packages/db/explain-plans/` carries this disclosure verbatim in its own body, not only in this record:

> This EXPLAIN was captured against an unseeded/minimally-seeded local database (a handful of synthetic rows), not FULL-PRODUCT-DEFINITION.md §37.4's production-scale dataset (500 channels / 2,000,000 payments / 5,000,000 alert events / 200,000 supporter identities). It is a plan-shape change detector only — proof that the query still resolves to the same kind of plan (index scan vs. sequential scan) as when it was last captured — and it is NOT evidence that any §19.4 performance budget is met at production scale.

**What it genuinely catches:** a plan-**shape** regression — a sequential scan appearing where an index scan was previously captured, a join algorithm changing, an index being dropped or renamed out from under a query — the exact class of defect a query-text edit can silently introduce. **What it does not do:** establish that any of these nine queries meets any §19.4 duration budget (50ms/100ms "any query on a live path", or the 150ms/200ms read path) at production volume. That remains RT-07's and the Phase 0.5 environment workstream's territory, both explicitly out of this row's scope, per `07_BUILD_BOOTSTRAP_AUTHORITY.md` §3.

Per the operator's own binding instruction, plan assertions in the artifacts are **shape** assertions (scan type, index used) rather than timing numbers — timing from an unsized local database is noise that would make the check flaky and untrustworthy; `EXPLAIN ANALYZE`'s own actual-time figures are captured (for transparency and future comparison once a sized environment exists) but are never asserted against by `check-plans.mjs`.

## Mechanism

**Correction to this row's own original premise, found during capture (recorded here per the operator's "if something in this command is factually wrong about the code, STOP and report it" rule).** The initial assumption — that because these ten functions are `language sql stable`, `EXPLAIN select * from app_private.<fn>(...)` would show Postgres's inlined join/scan plan directly — does not hold. Every one of the ten functions is additionally `security definer`, and PostgreSQL's planner categorically refuses to inline a SECURITY DEFINER SQL function regardless of `STABLE`/`IMMUTABLE` (`inline_function()` in the backend optimizer: `if (funcform->prosecdef) goto fail;` — inlining would let the body run with the *caller's* privileges/search_path instead of the definer's, which Postgres will not risk). So the literal `EXPLAIN SELECT * FROM app_private.<fn>(...)` call reliably produces only an opaque `Function Scan on <fn>` node, on every Postgres version, never the real join/scan detail.

Each artifact therefore captures **two** plans: (1) the literal function-call `EXPLAIN` exactly as originally specified (kept, for reproducibility, even though it is opaque), and (2) a supplementary "unwrapped" `EXPLAIN` of the function's own body with its parameters substituted by the same seeded literal values — the identical SQL text the `query_hash` below covers — which Postgres plans and executes as an ordinary query and which does surface the real index/sequential-scan nodes. **7 of 10 widgets unwrap fully** (goal, challenge, vote, paid-vote, recent-tips, supporter-ticker, mega-tip-banner). **3 of 10** (hype, leaderboard, top-supporters) call a second `security definer`/`plpgsql` helper internally (`hype_mode_state`, `channel_leaderboard`) that stays opaque even in the unwrapped capture, for the identical non-inlining reason one level deeper — noted individually in each of those three artifacts rather than glossed over.

For each widget, `packages/db/explain-plans/<widget>.explain.md` carries: the function's `file:line`; both exact queries run (literal and unwrapped); a `query_hash` — a sha256 of the function's `create or replace function … as $$ … $$;` body text, extracted from the migration file at capture time (this is what `check-plans.mjs` re-verifies — independent of which of the two EXPLAIN forms is more legible, the hash always covers the function's real, complete SQL text); the capture date and Postgres version; the disclosure sentence above verbatim; a one-line plan-shape summary naming which nodes stayed opaque, if any; and the full raw `EXPLAIN (ANALYZE, BUFFERS, FORMAT TEXT)` output for both forms.

`packages/db/explain-plans/check-plans.mjs` is dependency-free and needs no live database connection (so it can run in CI, or as part of `pnpm contracts:validate`-style checks, without a Postgres container): for each artifact it re-extracts the SAME function body from the CURRENT migration file, recomputes the hash with the SAME method, and compares it to the artifact's recorded `query_hash`. A mismatch means the query's SQL text changed since its plan was last captured — RT-12.2 — and the script exits non-zero, naming every widget whose plan is stale. Wired as `pnpm explain:check` in `bharatstudio-alerts/package.json`.
