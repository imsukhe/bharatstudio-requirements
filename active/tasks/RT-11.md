## Enforcement: why the timeout is structural, not conventional

The timeout attaches to a Postgres session at connection-open time (`connection: { statement_timeout }` in the pool's constructor options — verified against the installed `postgres@3.4.9` source, `node_modules/.pnpm/postgres@3.4.9/.../src/index.js`, not assumed from documentation alone), on a **physical pool that only ever serves the five read-only stores RT-10 wires to it**. A payment-order write (`routes/public.ts`'s tip-order POST), a webhook commit (`payment-webhook-go`, a separate Go service with its own connections), or a migration (`packages/db/migrations/*.sql`, applied by tooling entirely outside this Node process) **structurally cannot** reach this pool — there is no code path by which any of them is ever constructed with `derivedReadSql` instead of the main `sql`. `RT-11.2`'s test documents this boundary explicitly rather than merely asserting it holds by inspection.

The five stores this timeout can ever apply to (`overlayGoals`, `overlayChallenges`, `interactionOverlay`, `paidVoteOverlay`, `paymentLedger`) were each verified, by reading their full source before wiring, to contain **zero** `insert`/`update`/`delete` statements — every one is a single `select … from app_private.…` read. A statement timeout on any of them can only ever cancel a read, never a write, independent of and in addition to the pool-boundary argument above.

## Startup validation (RT-11.4)

`config.ts`'s `loadConfig` rejects `WIDGET_ANALYTICS_STATEMENT_TIMEOUT_MS` below **200** at startup: `"WIDGET_ANALYTICS_STATEMENT_TIMEOUT_MS must be at least 200 (FULL-PRODUCT-DEFINITION.md §19.4 API read p99 budget) when set"`. 200 is not invented — it is §19.4's own stated "API p99 < 200ms for reads" boundary, the same number `observability/metrics.ts`'s `READ_DURATION_BUCKETS_MS` already uses as its RT-06 bucket boundary for this exact class of request. A timeout configured below a compliant query's own budget would cancel queries that are, by definition, still within budget — a self-defeating misconfiguration this validation makes unreachable rather than silently degrading correctness.

## Boundaries

**In scope:** `statement_timeout` applied only via `db/derived-read-pool.ts`'s pool (shared with RT-10), only for the five read-only stores named above; SQLSTATE `57014` → `ReadTimeoutError` translation (`isStatementTimeoutError`, `runDerivedRead`, `wrapWithReadTimeout`); startup validation against §19.4; one counter.

**Explicitly out of scope, not touched:** every item RT-10's task record lists under its own Boundaries section applies identically here (RT-07, RT-09, RT-13, PRF-02, YouTube/marketing/pricing/tier work, RT-03, RT-04/RT-05's webhook/dispatch behaviour, `TC-RT-04`'s coalescing follow-up, the dead overlay-events parameters, `bharatstudio-crons`). No register state letter changed. **Widening this timeout to any other read path in the codebase (there are many GET routes this task's classifier marks `derived_read` by its fail-safe default but that were not individually wired to `derivedReadSql`) is deliberately left undone** — see the review record's decision log for why the scope was drawn at these five stores rather than "every GET route the classifier could reach," and what evidence would justify widening it.
