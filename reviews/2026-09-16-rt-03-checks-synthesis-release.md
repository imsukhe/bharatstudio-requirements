## 2. Design decisions this command did not settle

1. **`TtsQuotaMeter.release` is a required interface member, not optional.** `TtsStore.storeFallbackReason` remains optional (back-compat, pre-existing). RT-03.6 is named a blocking acceptance test by the operator's command, and a charge-on-failure defect is exactly the class of bug that an *optional* release method would allow to silently recur for a future caller that forgets to wire it. The cost was mechanical: 10 pre-existing `TtsQuotaMeter` object-literal fakes across three test files (`tts-quota-metering.test.ts`, `l07-mute-synthesis-cost-gate.test.ts`, `tts-fallback-reason.test.ts`) each gained `async release() {}`; no existing assertion in any of those files was changed.
2. **`app_private.release_tts_usage_reservation` (migration `0128`) decrements the existing `alert_tts_usage_monthly.characters_used` accumulator**, floored at zero, rather than introducing a new ledger table or a new `entry_type`. §10.2 lists grant/reserve/settle/release/refund/expiry as the complete vocabulary for the AI-credits ledger; the TTS character quota's actual implementation (migration `0081`) has always been a per-channel/per-month counter, not literal ledger rows. This is a release over the existing mechanism — the operator's instruction was to follow whatever reserve/settle/release shape the codebase already uses and not invent a new entry type, and the codebase's existing shape here is a counter, not a row-per-event ledger.
3. **A 5xx or a 429-with-`Retry-After` from the internal worker→API TTS route is classified retryable-unambiguous** on the reasoning that a complete HTTP response (status line and headers received by Go's `net/http` client) means the request definitely reached `apps/api`'s internal route and got a definitive answer — and, after this task's own quota-release fix, that any error response from that route is now guaranteed to have already released any reservation before it left the route. This is an inference specific to the current single-hop worker→API topology, not a literal "5xx received before any response body" byte-level distinction (the operator's own §19.0 RT-03 text uses that phrase; Go's `http.Client` does not expose a "before any body" signal distinct from "a response with a 5xx status was received" at this call site, and no authority defines the distinction more precisely than that). **Unverified**: whether `apps/api`'s own internal TTS route could ever, under some failure mode, return a 5xx *after* already streaming a partial success body that a caller could misinterpret — reviewed the route (`apps/api/src/routes/tts.ts`) and found no such path (every response is a single `reply.code(...).send(...)` call, never a stream), so this is asserted with reasonable confidence rather than left fully open, but it was not exhaustively proven against every possible Fastify failure mode (e.g. a connection drop mid-write of a 200 response is not the same as a 5xx and is out of scope for this classification).
4. **No new metric was added on the Go side.** RT-06 (histograms) is explicitly excluded from this task. RT-02's precedent of adding bounded *counters* for its own observability need was not repeated here, because the operator's command for this task names only `Logger.Event` (not a metrics counter) for the Go-side privacy/security requirement, and adding an unrequested counter would be scope drift. A bounded `tts_enrich` outcome counter remains a reasonable, additive follow-up if operability ever needs it — not proposed here as a requirement.
5. **The `register-map.tsv`/`semantic-mapping-audit.md` `state` cell for `RT-03` stays `X`**, matching `FULL-PRODUCT-DEFINITION.md` §31.18.0's own `RT-03` row exactly, per the operator's explicit instruction not to change that letter. `lifecycle` moves from `new-record-required` to `active-record` because a real ten-field record (`active/tasks/RT-03.md`) now exists — mirroring RT-02's precedent, where `P`/`active-record` also left the register's own state letter for Opus to move only after audit.

## 3. The charge-on-failure finding — confirmed, and fixed inside this task

**Confirmed present before this task.** `apps/api/src/routes/tts.ts` called `quotaMeter.meter(input.eventId, input.message.length)` — which `app_private.meter_tts_usage` (migration `0081`) settles **unconditionally and immediately**, incrementing `alert_tts_usage_monthly.characters_used` in the same statement that returns `allowed: true` — and only *afterward* called `service.synthesize(...)`. On every synthesis-failure path after that point (a provider throw, caught and re-thrown as a 500; or a `{ mode: 'chime' }` result from a provider timeout/failure), the already-settled charge was never returned. A creator could be charged premium characters for audio nobody ever heard, repeatedly, with no route back to the balance. This is exactly the defect the operator's command anticipated and required to be fixed inside this task, not merely flagged.

**Fixed.** `apps/api/src/routes/tts.ts` now records `reservedCharacters = input.message.length` immediately after a successful `meter()` call, and calls `quotaMeter.release(input.eventId, reservedCharacters)` on both synthesis-failure paths (the catch block, before the error re-throws; and the `result.mode === 'chime'` branch, before responding) before any response leaves the route. `app_private.release_tts_usage_reservation` (migration `0128`) is the SQL half: it decrements the same monthly counter by exactly the given amount, floored at zero, under the same `channels`-row lock discipline `meter_tts_usage` already uses, so a concurrent reserve/release for the same channel serializes correctly. Proven at both layers: `packages/db/tests/rt03_tts_quota_reservation_release.sql` (reserve→release restores the exact balance; double release is a safe no-op; partial release leaves the correct remainder) and `apps/api/test/tts-quota-metering.test.ts`'s four new RT-03.6 tests (release called with the exact metered character count on a provider throw and on a chime-mode result; never called on success; never called when nothing was reserved).
