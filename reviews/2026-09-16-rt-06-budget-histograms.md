## 1. Product/market/provider review (§2 of the operator's command)

Bounded, official-documentation-only research into what a histogram genuinely proves versus a summary, why cross-instance quantile aggregation cannot be an average, how bucket boundaries should be chosen, and what Cloud Run/Cloud Monitoring specifically requires to scrape and aggregate custom histogram metrics in a real deployment. Sources and access dates below; all fetched 2026-09-16.

### Prometheus — histogram vs. summary, and why an average cannot falsify a p99

- **[Histograms and summaries | Prometheus docs](https://prometheus.io/docs/practices/histograms/)** — accessed 2026-09-16. On the two metric types: a summary "calculates a number of pre-configured quantiles... over pre-configured time windows... and exposes them as additional metrics," while a histogram instead "represents the distribution in a more fundamental way that can later be used to calculate arbitrary quantiles over arbitrary time windows," with "observations... counted in buckets." **On aggregation, quoted directly and load-bearing for this whole task**: *"aggregating the precomputed quantiles from a summary rarely makes sense... averaging the quantiles yields statistically nonsensical values. `avg(http_request_duration_seconds{quantile="0.95"}) // BAD!`"* This is the documented reason RT-06 exists: the pre-RT-06 code (`apps/api/src/observability/metrics.ts`'s `bsa_api_request_duration_ms_sum` divided by `bsa_api_requests_total`) is exactly a mean, one step short of even a summary's precomputed-but-unaggregable quantile — an average is not a p99 and cannot falsify one, confirmed here in the tool's own documentation rather than asserted from first principles. On bucket selection: *"Pick buckets suitable for the expected range of observed values and the desired queries."* No fixed rule beyond that is documented — consistent with this task's own binding rule (§3.1 of the operator's command) that a budget number, not an external convention, is what fixes each boundary. On interpolation: *"the `histogram_quantile()` function interpolates the quantile value within the bucket the quantile value falls into"*, assuming uniform distribution, and explicitly: *"given the bucket boundaries above, the true value could be anywhere between 210ms and 229ms, depending on the actual distribution of requests within the bucket"* — the documented source for this task's own repeated HELP-text disclosure that every p95/p99 gauge is a bucket-width-bounded estimate, never an exact value (§3.2).

### Prometheus — cross-instance aggregation is additive, at query time, over the cumulative wire format

- **[`histogram_quantile()` | Prometheus query functions](https://prometheus.io/docs/prometheus/latest/querying/functions/#histogram_quantile)** — accessed 2026-09-16. Quoted directly: *"To aggregate, use the `sum()` aggregator around the `rate()` function. Since the `le` label is required by `histogram_quantile()` to deal with classic histograms, it has to be included in the `by` clause"* — worked example: `histogram_quantile(0.9, sum by (job, le) (rate(http_request_duration_seconds_bucket[10m])))`. This is the documented mechanism §19.0's "aggregated across instances" requirement rests on: **per-instance bucket counts are counters, counters are additive, so summing them across an `instance` label before calling `histogram_quantile` is correct; averaging the already-computed *quantiles* (the summary approach, previous section) is not.** This directly grounds this task's own `mergeHistograms`/`MergeHistograms` pure functions (RT-06.4) — they are the local, testable half of exactly this `sum by (le)` operation, proven correct as elementwise addition over per-slot bucket counts.

### OpenTelemetry — the histogram data model, confirmed to match what this task built

- **[Histogram | OpenTelemetry metrics data model](https://opentelemetry.io/docs/specs/otel/metrics/data-model/#histogram)** — accessed 2026-09-16. Quoted directly: a histogram consists of "a series of buckets with: Explicit boundary values... A count of the number of observations that fell within this bucket," plus "a count (`count`) of the total population of points" and "a sum (`sum`) of all the values." Bucket-edge convention, quoted: *"Bucket upper-bounds are inclusive... while bucket lower-bounds are exclusive"* — exactly the `(lower, upper]` convention this task's `observeHistogram`/`Histogram.Observe` implement in both languages. On multi-source aggregation: *"Every OTLP data stream has an intrinsic decomposable aggregate function making it semantically well-defined to merge data points across both temporal and spatial attributes"* — independent, second-standard confirmation (alongside Prometheus's `sum by (le)`) that histogram bucket counts are the correct additive unit for cross-instance combination, not the derived quantile. The codebase does not use OpenTelemetry (§19.1's stack table names Prometheus text exposition, in place today); this citation is background confirming the chosen shape is the industry-standard one, not a recommendation to adopt OTel here.

### Google Cloud Monitoring / Cloud Run — what is achievable locally versus what requires a deployed environment

- **[Metric kinds, types, and value types | Cloud Monitoring](https://docs.cloud.google.com/monitoring/api/v3/kinds-and-types)** — accessed 2026-09-16. Confirms Cloud Monitoring's own histogram-shaped value type: *"For distribution measurements, the value isn't a single value but a group of values. The value type for distribution measurements is `DISTRIBUTION`"*, and *"A distribution contains statistics that summarize a group of values."* This document did not state how `DISTRIBUTION`-valued custom metrics are aggregated across instances (that question is answered instead by the Prometheus sidecar path below, which is the actual mechanism this stack would use — §19.1 names Prometheus text exposition, not the Cloud Monitoring API's native `DISTRIBUTION` type, as the current in-place format).
- **[Write Prometheus metrics by using the Prometheus sidecar | Cloud Run](https://docs.cloud.google.com/run/docs/monitoring-managed-prometheus-sidecar)** — accessed 2026-09-16. This is the concrete, named mechanism by which this codebase's existing `/internal/metrics` text-exposition endpoints would actually be scraped in a deployed Cloud Run environment: *"If you don't create a custom `RunMonitoring` configuration, then the sidecar collector synthesizes a default configuration to scrape metrics from port 8080 at metrics path `/metrics` every 30 seconds."* Per-instance identity is preserved at scrape time: *"The `instance` label is always set to the Cloud Run instance ID."* **This is the load-bearing finding for what is achievable locally versus not.** The sidecar "relies on the Cloud Run multi-container (sidecar) feature to run the collector as a sidecar container alongside your workload container" — a deployment-time mechanism with no local-process equivalent. Concretely, this means: (a) the *exposition format* — bucket lines, `le` labels, `_sum`/`_count` — is fully provable locally, and is (RT-06.1, RT-06.2, RT-06.7); (b) the *additive property* two histograms' bucket counts sum to the arithmetically correct combined histogram is fully provable locally as a pure function, and is (RT-06.4); (c) the *actual per-instance scrape, the `instance` label attachment, and the real `sum by (le, instance)`-then-`histogram_quantile` aggregation across genuinely different Cloud Run instances* requires the sidecar, a deployed multi-instance Cloud Run service, and Cloud Monitoring itself — none of which this task stands up or claims. **RT-07 and the Phase 0.5 environment workstream (`bharatstudio-requirements/active/launch/07_BUILD_BOOTSTRAP_AUTHORITY.md` §3) are where that deployed proof belongs; this task explicitly does not claim it.**

## 2. Bucket-boundary derivation — every boundary justified against a §19.4 budget

**TS `READ_DURATION_BUCKETS_MS` = `[10, 25, 50, 75, 100, 150, 200, 300, 500, 1000]`.** §19.4: *"API p99 | < 200ms for reads."* **200 is the exact stated budget** — present verbatim as a bucket boundary, so `bsa_api_read_duration_ms_bucket{le="200"}` divided by `..._count` is directly, non-interpolated, the fraction of reads at or under budget. `10/25/50/75/100/150` resolve how far under budget normal traffic runs (invisible with only a single 200 boundary); `300/500/1000` size how far over budget a regression runs. None of these six is itself a budget; each is a resolution step bracketing the one number that is.

**TS `TIP_ORDER_DURATION_BUCKETS_MS` = `[50, 100, 200, 300, 400, 500, 750, 1000, 2000]`, reused verbatim as `payment-webhook-go`'s `tipOrderClassBucketsMs`.** §19.4: *"< 500ms for the tip-order path."* **500 is the exact stated budget.** `50/100/200/300/400` resolve the common case below budget (this path makes a live outbound call to Razorpay via the Go service, so sub-budget resolution matters for triage); `750/1000/2000` size overshoot.

**`payment-webhook-go`'s `bsa_payment_webhook_ack_duration_ms` (the `/v1/webhooks/razorpay` path) reuses the same 500ms tip-order-class bucket set — a classification, stated plainly, not a third invented number.** §19.4 names this path only by an ordering rule ("2xx after the durable commit, never after a dispatch call"), no duration figure. The operator's command (§3.5) explicitly lists this path as one RT-06 "may add measurement to... beyond" RT-04/RT-05's existing behaviour, so leaving it entirely unmeasured would contradict the command's own scope statement; inventing a bespoke number would violate the binding rule ("bucket boundaries are not yours to invent"). The 500ms tip-order-class set is the reasoned middle path: both this path and the tip-order path are payment-commit HTTP requests (verify → durably persist → respond), so the same budget class applies by structural analogy, using **only** a number §19.4 already states, applied to a second path within the same class rather than fabricated for this one. Recorded here explicitly, per the binding rule's own instruction, rather than asserted quietly in a code comment alone.

**`alert-worker-go`'s `bsa_worker_pump_duration_ms` (the `/internal/v1/tasks/pump` path) uses the read-class 200ms bucket set, by the same reasoning pattern.** §19.4 names no duration for this path either — it is RT-04/RT-05's dispatcher trigger, invoked by a fire-and-forget wake-up or the scheduled `outbox-recovery` tick, never awaited by an external caller. Of the two budgeted classes, it is the closer analogue of "API reads": a bounded, internal, no-external-provider-call operation, unlike the tip-order path's live outbound Razorpay call. Same discipline as above: a reasoned classification onto an existing §19.4 number, not an invented one, recorded explicitly rather than left implicit.

**`alert-worker-go`'s `/internal/v1/tasks/overlay` path was deliberately left uninstrumented by a duration histogram.** No §19.4 row names a duration for it, and no structural analogy to either budgeted class was clear enough to state without more confidently guessing at its purpose than the codebase justifies from this review alone (unlike the pump trigger, whose role RT-04/RT-05 already fully specify). Left as existing counters only, consistent with "if you find yourself picking a number... STOP and report it" — reported here, not silently instrumented.

## 3. What is proven locally versus what requires a deployed environment — stated plainly, per §3.3

**Proven locally, with a passing test cited for each:** the Prometheus text-exposition shape for every new histogram, including the exact §19.4 boundary as a bucket line (RT-06.1); arithmetically exact bucket counts from a known set of observations (RT-06.2); a p95/p99 estimate that falls within the documented bound of the bucket containing the true value, for a known distribution (RT-06.3); the additive property that makes cross-instance summation correct — two independently observed histograms over the same bucket set sum, bucket-by-bucket, to the exact combined histogram (RT-06.4); zero-label discipline (RT-06.5); no panic/throw and no request-path effect from a pathological value or a broken durable read (RT-06.6); the existing exposition shape unbroken for every pre-RT-06 metric (RT-06.7); durable, cross-session (simulating cross-instance) correctness of the reconciliation snapshot, at both the Postgres level (separate `\connect` sessions) and the TS route level (`GET /internal/metrics` on an instance with no in-memory snapshot of its own) (RT-06.8); Go `-race` cleanliness of every new shared histogram field under concurrent `Observe`/`WritePrometheus` (RT-06.9).
