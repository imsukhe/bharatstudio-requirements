### PostgreSQL — `statement_timeout`, `idle_in_transaction_session_timeout`, connection limits, `EXPLAIN`

- **[Client Connection Defaults — Statement Behavior | PostgreSQL 16 documentation](https://www.postgresql.org/docs/16/runtime-config-client.html)** — accessed 2026-09-16. `statement_timeout`, quoted: *"Abort any statement that takes more than the specified amount of time. ... A value of zero (the default) disables the timeout."* Units default to milliseconds when unspecified — the exact unit RT-11's `WIDGET_ANALYTICS_STATEMENT_TIMEOUT_MS` env var and `derived-read-pool.ts`'s `Math.floor(...)` assume. Load-bearing caveat, quoted: *"In extended query protocol, the timeout starts running when any query-related message (Parse, Bind, Execute, Describe) arrives, and it is canceled by completion of an Execute or Sync message"* — confirms the timeout genuinely bounds the statement's server-side execution window, not merely a client-side wait, which is what makes RT-11.1 ("releases its connection") true: Postgres itself reclaims the connection on cancellation, this application does not need a second mechanism to force it. Also quoted, and the reason RT-11 places its mechanism on a dedicated pool rather than `postgresql.conf`: *"Setting `statement_timeout` in `postgresql.conf` is not recommended because it would affect all sessions."* RT-11 does exactly the recommended narrower thing — a per-pool, per-session-parameter setting (`connection: { statement_timeout }`), reaching only the sessions on the derived-read pool.
- Same page, `idle_in_transaction_session_timeout`, quoted: *"Terminate any session that has been idle ... within an open transaction for longer than the specified amount of time. ... A value of zero (the default) disables the timeout."* Read as background per the operator's list; not used by this task — none of the five governed stores opens a multi-statement transaction (each is a single `select`), so there is no idle-in-transaction window for this row to bound. Recorded here so a future reader does not wonder why it was read but not implemented.
- **[EXPLAIN | PostgreSQL 16 documentation](https://www.postgresql.org/docs/16/sql-explain.html)** — accessed 2026-09-16. Quoted, the core mechanism RT-12 relies on: *"This command displays the execution plan that the PostgreSQL planner generates for the supplied statement. The execution plan shows how the table(s) referenced by the statement will be scanned — by plain sequential scan, index scan, etc."* On `ANALYZE`, quoted: *"causes the statement to be actually executed, not only planned. Then actual run time statistics are added to the display."* This is exactly the load-bearing caveat behind RT-12's own "change detector, not proof" framing — actual run-time statistics from an unseeded table are close to meaningless, but the **plan shape** (scan node choice) is still real Postgres planner output, not a fabrication. Also quoted, directly informing why `pg_statistic` freshness matters and why a plan captured on 2-5 synthetic rows can legitimately differ from one captured at production volume: *"In order to allow the PostgreSQL query planner to make reasonably informed decisions when optimizing queries, the `pg_statistic` data should be up-to-date for all tables used in the query."* A cost-based planner routinely prefers a sequential scan over an available index on a near-empty table — this is correct planner behaviour, not evidence of a missing index, and every artefact that shows one says so explicitly rather than reading it as a defect.

### Google Cloud SQL / Cloud Run — connection limits and concurrency, why RT-10's pool isolation is the right shape here

- **[Quotas and limits | Cloud SQL for PostgreSQL](https://docs.cloud.google.com/sql/docs/postgres/quotas)** — accessed 2026-09-16. Quoted: *"When you create a Cloud SQL for PostgreSQL instance, the machine type configuration settings automatically adjust the range of memory sizes available, based on the number of cores you select. This also determines the initial default connection limits set for the instance."* Confirms `max_connections` is a fixed, sized, shared budget across every service and pool that connects to the instance — the structural reason a widget/analytics burst consuming that shared budget can starve a payment write, which is RT-10's entire premise. This document did not state a specific number for any particular machine size (it directs the reader to query `pg_settings` on the actual instance), so — consistent with §2 of the owning command — no specific connection-count number is asserted anywhere in RT-10/RT-11's code or these records; the mechanism is built to be configured against whatever the real production limit turns out to be, not against a guessed figure.
- **[About concurrency | Cloud Run](https://docs.cloud.google.com/run/docs/about-concurrency)** — accessed 2026-09-16. Quoted: *"Cloud Run instances deployed using Google Cloud CLI or Terraform have a maximum concurrency that is 80 times the number of vCPUs... You can configure the maximum concurrent requests per instance. You can increase this to a maximum of 1,000."* And, the specific finding that makes RT-10's in-process admission governor meaningful rather than redundant: *"when concurrency is enabled, Cloud Run does not provide isolation between concurrent requests processed by the same instance"* — many requests share one instance's CPU and, transitively, its share of the database connection pool, with no platform-level fairness between a payment write and a widget read arriving on the same instance at the same moment. That is exactly the gap RT-10's admission governor and isolated pool fill; Cloud Run's own concurrency model does not fill it for this application.

### postgres.js (the library, verified against the exact installed version)

- **[porsager/postgres README, `max` connections](https://github.com/porsager/postgres)** — accessed 2026-09-16. Quoted: *"When there are high amount of concurrent queries, `postgres` will open as many connections as needed up until `max` number of connections is reached. By default `max` is 10."* This codebase's own existing secondary-pool precedent (`db/public-channel-repository.ts`'s `createSqlClient`, `max: 10`, pre-dating this task) matches the library's own default exactly — confirming `DEFAULT_DERIVED_POOL_MAX = 10` in `derived-read-pool.ts` is reusing two independent existing numbers (this codebase's own precedent AND the library default), not inventing a third.
- Same README, on session parameters: *"Other connection parameters, see https://www.postgresql.org/docs/current/runtime-config-client.html"*, with a documented example passing `statement_timeout` inside the `connection` option. **Verified beyond the README, against the actually-installed `postgres@3.4.9` source** (`node_modules/.pnpm/postgres@3.4.9/node_modules/postgres/cjs/src/index.js` and `src/connection.js`) rather than trusted from documentation alone, because the README's own example shows a string value (`'30s'`) while the installed version's TypeScript types declare `ConnectionParameters.statement_timeout: number` — a real discrepancy between the README and this specific installed version that `tsc` caught during implementation (`apps/api/src/db/derived-read-pool.ts` originally passed a string and failed to build; fixed to pass a number). Read directly, `options.connection` entries are merged into the Postgres wire-protocol `StartupMessage` (`connection.js`'s `StartupMessage()` function folds `options.connection` into the startup parameter list sent on every new physical connection) — confirming this is a real, once-per-physical-connection Postgres session parameter, not a per-query option this library reissues, which is why RT-11's mechanism must create a dedicated pool to attach a timeout at all (there is no per-query timeout parameter in this installed version).

## 2. Design decisions this command did not settle

1. **RT-10 and RT-11 share one classifier and one pool rather than each inventing its own.** `read-priority.ts`'s `classifyReadPriority` is consulted by both; `derived-read-pool.ts`'s `createDerivedReadSql` provides both the isolated pool (RT-10) and the timeout wrapper (RT-11) from one function. This was a deliberate simplification over an earlier draft that gave RT-11 its own `SET LOCAL statement_timeout`-per-call mechanism usable even without RT-10's separate pool — dropped because it required wrapping every call in its own single-statement transaction (`sql.begin(...)`), which is a bigger behavioural change to each read (transaction semantics on what is otherwise a plain autocommit `select`) for a rare configuration combination (timeout without pool isolation) that the operator's own scope discussion never asked for. The simpler, shipped version: when `WIDGET_ANALYTICS_STATEMENT_TIMEOUT_MS` is set without `WIDGET_ANALYTICS_POOL_MAX`, a real pool is still created (defaulting to `DEFAULT_DERIVED_POOL_MAX = 10`, §1's postgres.js/codebase-precedent citation above) because RT-11's timeout has no per-query attachment point in this library version and genuinely needs *some* pool to set a session parameter on.
2. **Scope was drawn at five specific stores (`overlayGoals`, `overlayChallenges`, `interactionOverlay`, `paidVoteOverlay`, `paymentLedger`), not "every GET route the classifier marks `derived_read`."** RT-10's own row text names "widget, dashboard and analytics reads" — read narrowly, as the concrete surfaces this codebase actually has (the nine named widgets plus the one dashboard/ledger read that already existed with its own isolated read-only store), rather than broadly, as "every non-exempt GET route in the application," which would have meant touching dozens of unrelated store files (account settings, channel config, `/v1/me`, etc.) for surfaces the operator's command never named and that carry no evident backpressure risk. `classifyReadPriority`'s fail-safe default still marks every one of those OTHER GET routes `derived_read` (so a future operator who wires them in gets the safe default, not an accidental payment-class exemption), but this task did not wire the isolated pool/timeout to any of them. **Referred to Opus:** whether that broader wiring is in-scope follow-up work, and if so, under which row.
3. **RT-12's artefacts assert plan shape, never a duration, by design (not an oversight).** The operator's command states this explicitly as a binding rule ("prefer plan shape assertions... because timings from an unsized local database are noise"); this review confirms it against PostgreSQL's own documentation (§1 above — `ANALYZE`'s actual-time figures depend on `pg_statistic` being representative, which a throwaway 2-5-row seed is not) rather than merely repeating the instruction.
4. **The factual correction about `apps/api/src/app.ts`'s `max: 120`** (recorded in full in `active/tasks/RT-10.md`'s Boundaries section) changed which number `derived-read-pool.ts` treats as this codebase's existing pool-size precedent — 10, from `public-channel-repository.ts`, not 120. No design decision in this slice was based on the incorrect 120 figure; it was caught before any code was written against it (the confusion was in the OPERATOR's briefing text, not in any implementation this task produced).

## 4. Data-plane capture (RT-12) — filled in from the capture agent's own report

**Setup.** A throwaway `postgres:16-alpine` container (`rt12-explain-pg-80132`, port 55440, removed with `docker rm -f` on completion — the running dev container `bharatstudio-alerts-postgres-1` was never touched). `packages/db/roles/0001_v1_service_roles.sql` plus all 130 files in `packages/db/migrations/` applied in ascending order via `psql -v ON_ERROR_STOP=1` — clean apply, zero errors.

**Seed data.** One channel/session/owner, 2 `support_goals`, 2 `paid_challenges`, 3 `interaction_definitions` (hype/free-vote/paid-vote) with their vote options/records and one `hype_mode` activation, 2 viewer accounts/identities, payment accounts/order intents, 5 payments, 2 alert events, and 1 vote-payment tag — all scoped to one seeded overlay session (`token_fingerprint = sha256("rt12-explain-capture-token")`). **All 10 widgets returned real, non-zero-row EXPLAIN captures — none fell back to a zero-row/empty-table plan.**

**The inlining correction (§3.1 restated from `active/tasks/RT-12.md`).** All ten target functions are `security definer` in addition to `language sql stable`; PostgreSQL's planner never inlines a SECURITY DEFINER function (verified against `inline_function()`'s `prosecdef` check, and confirmed empirically by the capture itself — every literal `EXPLAIN SELECT * FROM app_private.<fn>(...)` produced an opaque `Function Scan` node). Each artifact therefore carries both the literal function-call `EXPLAIN` (as originally specified, kept for reproducibility) and a supplementary "unwrapped" `EXPLAIN` of the function body with the same seeded literal parameter values substituted in, which Postgres plans as an ordinary query and which does show real index/sequential-scan nodes. **7 of 10 widgets unwrap to a fully resolved plan with no opaque sub-nodes** (goal, challenge, vote, paid-vote, recent-tips, supporter-ticker, mega-tip-banner — each showing real `Index Scan` nodes against `overlay_sessions` and the widget's own table, e.g. goal's `Nested Loop(Index Scan using overlay_sessions_pkey on overlay_sessions, Index Scan using support_goals_channel_active_idx on support_goals)`). **3 of 10 (hype, leaderboard, top-supporters) call a second `security definer`/`plpgsql` helper internally** (`hype_mode_state`, `channel_leaderboard`) that remains its own opaque `Function Scan` node even in the unwrapped capture, for the identical non-inlining reason one level deeper — disclosed individually in each of those three artifacts rather than presented as fully resolved when it is not.

**Verification.** `node packages/db/explain-plans/check-plans.mjs` (and `pnpm explain:check`) — `OK: 10/10 plans current`, exit 0. The capture agent additionally verified the negative case: tampering with one artifact's recorded `query_hash` makes the check fail (exit 1, naming the affected widget), then restored it — proving the change-detector genuinely detects drift rather than trivially passing.

**Files:** `packages/db/explain-plans/{goal,challenge,hype,leaderboard,vote,paid-vote,recent-tips,top-supporters,supporter-ticker,mega-tip-banner}.explain.md`, `packages/db/explain-plans/check-plans.mjs`, and the `"explain:check": "node packages/db/explain-plans/check-plans.mjs"` line added to `bharatstudio-alerts/package.json`'s `scripts` (added after `contracts:route-inventory`; nothing else in that file changed).
